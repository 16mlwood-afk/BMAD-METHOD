# Design-Handoff State Variables — Rationale Appendix

This file exists for **context budget** (see `mason-bmad-workflow-expert/references/context-budget.md`). The orchestrator `workflow.md` is re-read on every run; its `### State Variables` block is the index (name · allowed values · where set). The *rationale* — why a variable exists, the failure it guards, the cross-variable contract — lives here and is read on demand, so the hot path stays cheap. **Load-bearing semantics also live at point-of-use in the step files** (step-01b/01c decide most of these; step-03 renders them); this appendix is the consolidated "why", not a second source of truth for the contract.

Only the variables whose definition carried multi-sentence rationale are documented here. Pure one-liners (`{feature_name}`, `{api_surface}`, `{implementation_files}`, etc.) need no appendix entry — their workflow.md line is complete.

---

## `{surface_class}` — pages get the page machinery; chrome gets none of it

`page` (default) | `chrome`. Set FIRST, in step-01 §0, before any capture runs. `chrome` = app-shell surfaces (global nav, sidebar, top-bar, mobile nav drawer, the shell frame): `page_mode` becomes `n/a`, the data-walk/finance/band/drawer machinery (§3–§3b, §5–§5g, step-01b) is skipped, and the chrome-equivalent captures run instead (route inventory · per-item states · role visibility · breakpoints). The visual system and anti-AI hard failures apply verbatim — chrome is exempt from page COMPOSITION rules, never from the design system. Contract + consumer obligations (don't enforce page-mode composition against chrome): `shared/brief-revision-policy.md` Block B `surface_class` row + invariant 1a. Exists because forcing the page template onto a nav redesign fabricates `page_mode`/`composition` metadata that strict consumers then enforce against a surface they don't model (fork-gaps 2026-07-02, nav-redesign).

## `{injected_placement}` / `{injected_archetype}` — the consumability contract

These carry an upstream decision (from `analytics-placement-triage`, or a direct `--placement`/`--archetype`) so this workflow **honors** it rather than silently re-deriving it. The point is the consumability contract: a placement/shape verdict made by the single-source brain upstream must not degrade into advisory prose that this workflow re-decides differently. When non-empty, §5b (band-belongs) / §5d (topology) / §5c (archetype) honor the injected value (after a §5b-style sanity gate) and skip re-derivation, threading provenance (`injected-by-triage`). Empty (the default) → fully derive as before — backward-compatible.

## `{must_support_capabilities}` — the anti-silent-drop "keep" list

The jobs the operator must accomplish on this surface beyond the primary goals, as **outcomes not UI mechanics**. These are requirements the blank-canvas redesign must satisfy even though the brief withholds the current layout — the anti-bias strip removes the *arrangement*, never the *capability*. Guards the failure where a redesign returns "more basic" than the screen it replaced because a secondary capability (attach-source-receipt, verify-field-against-source, bypass-staging) was never named and so was silently dropped. Empty only when the surface genuinely has none beyond the primary goals.

## `{dropped_capabilities}` — the anti-silent-drop "shed" log

Capabilities the current surface exposes that are **deliberately NOT carried into this brief**, each `{ capability (outcome phrasing) · backing_action · reason }`, reason ∈ `relocated` (to a named sibling) | `obsolete` | `out-of-scope-by-design`. The *log* half of the anti-silent-drop contract: `{must_support_capabilities}` records what the redesign must keep; this records what it deliberately sheds and WHY — so a drop is a visible, vetoable decision (surfaced at end-of-run by step-03 §5 and in the brief), never a silent omission. Never empty by omission — empty list only when every action the current surface invokes is carried forward. Blind spot it closes: a mutation on an existing record (resolve / remap / override / re-run) that is neither a primary goal nor an ingest endpoint, which recall-based capture misses (the EOS batch-detail remap loss).

## `{composition_provenance}` / `{composition_rationale}` — verify the composition, don't inherit it

`policy-default` | `recommended-alt`. WHETHER the page-mode's default composition (operational→table-first; analytical→chart-led; detail→record-view) fits the job — decided in §5a by the job, NOT inherited from the policy default or the legacy render. `recommended-alt` (veto-surfaced) means §4a names a different *primary* composition; it does NOT change `{page_mode}` (work type and composition are orthogonal). Guards the policy-default bias (Anti-Bias Principle II): stamping the mode's default composition unquestioned is a bias as real as inheriting the legacy layout, and harder to catch because it feels like correctly following the system. `{composition_rationale}` keeps the deviation auditable (the three §5a answers + named alt + veto outcome); empty when `policy-default`.

## `{spawned_surfaces}` — the Deliverable-Completeness contract

The secondary surfaces THIS page spawns at runtime, each a **required deliverable frame** in §7's Surface Inventory: the primary surface; the right-side detail drawer (present for `operational`/`analytical` under the table-first composition — for `page_mode: detail` the primary surface IS the drawer); one frame per `{linked_records_inventory}` entry (the §13 expand-in-context lookup drawers). Derived in §5f from `{page_mode}` + `{composition_provenance}` + `{linked_records_inventory}` — **NOT recalled**. Each entry: `{ frame_name · trigger · render_as (drawer-over-{parent} | full-bleed) · must_contain · figures (the §4d decision numbers) · lookups (depth-1 §2a fields) }`. Rendered by step-03 into §7, **frame-name keyed** so the same name travels brief → rendered frame → `design-implement` grid row with zero inference at any hop (Deliverable-Completeness Principle). **Depth-1:** a lookup drawer lists only its own immediate lookups; the foreign record's own §2a owns the next level (stops the recursive order→catalog→supplier graph from inlining). Empty only for a true leaf surface with no drawer and no linked records.

## `{band_provenance}` / `{has_analytics_band}` — band presence is a judgment, not an inheritance

`inherited` | `recommended-new` | `recommended-drop` | `none`. WHY an analytics band exists (or doesn't) — decided in §5b by data + user job, NOT by inspecting the legacy render. The blank-canvas mandate means a bare-table feature whose job is pattern/coverage/ranking work gets a band recommendation (`recommended-new`, veto-surfaced) even when the current page has none. Drives §4b inclusion: present iff `inherited` or `recommended-new`. `{has_analytics_band}` = `true` iff `band_provenance` ∈ {`inherited`, `recommended-new`} and gates §4b emission.

## `{analytics_archetype}` + the analytics reasoning capture — one selection brain

The *shape* of the band (one of nine archetypes, or `unclear` → ask). **Selected in §5c by invoking the `analytics-surface-architect` skill** — the single selection brain so handoff, design-review-pr, and a human all reason the same way (`shared/analytics-archetypes.md` is its taxonomy SoT). Chosen from the user's question, never the data's availability; prevents every band defaulting to the same trend-strip-of-small-multiples. The companion capture variables (`{archetype_candidates}`, `{archetype_winner_reason}`, `{archetype_secondary}`, `{time_present_check}`, `{archetype_drill_map}`, `{archetype_prohibited}`, plus the non-skill `{page_mode_rationale}` / `{band_decision_log}`) are the skill's decision object, captured at decision time and rendered by step-03b into the rationale artifact. Capturing it where the decision is made turns a discarded deliberation into an auditable record. Empty when there is no band.

## `{project_phase}` / `{is_greenfield}` — same brief shape, different input sources

The project lifecycle phase from config (`greenfield` | `brownfield` | `mixed`; absent ⇒ `brownfield`). `{is_greenfield}` = true iff `greenfield`. Governs step-01 §1c source binding: greenfield gathers §2–§4 from PRD + architecture + UX + the design-policy-as-spec (no built code), relaxes the §2-pre grounding gate to a settled-spec/policy basis, and skips step-02. The brief shape is phase-agnostic — only the INPUT SOURCES change (codifies `GREENFIELD-BRIEF-DERIVATION.md`). A greenfield brief is stamped `revision_mode: spec_derived` / `last_modified_by: human` in step-03 (`brief-revision-policy.md` §4).

## `{policy_version}` — drift detection downstream

Integer version of `docs/design-policy.md` at brief-generation time (`1` if no version field; `0` if no policy file). Stamped into the brief's `policy_version_required:` so downstream consumers (design-synthesize, design-implement) can detect when the policy has moved past the brief's pinned version.

## Finance-domain pass (`{is_finance_surface}` + the finance block) — capture meaning, never layout

Set in step-01 §3b only when the surface is finance-shaped; empty/absent otherwise. Produced by the `finance-domain-pass` skill (inline fallback if not synced). Captures finance MEANING for the brief, never layout:

- `{is_finance_surface}` — `true` iff a ledger / transactions / inventory movement / reconciliation / P&L / balance sheet / cash flow / FP&A surface. Gates §3b and the finance render in step-03.
- `{finance_report_type}` — detected finance report/data type. A §1 context signal — does NOT set `{page_mode}` or composition.
- `{finance_column_semantics}` — each source column → semantic group (`quantity|money|status|identity|date|meta`) + meaning; enriches `{data_shape}`. Quantity and value stay distinct. For money columns it also carries `basis` (`persisted | derived | unknown`) — a derived figure (computed at render) is labelled derived, never shown as a stored value (rendered at §4d).
- `{finance_exception_expectations}` — finance exceptions the design must be able to REPRESENT (missing cost, negative stock/value, reconciliation break, pending receipt, duplicate/exploded references, estimated-vs-actual) — as outcomes, not a panel design.
- `{finance_unresolved_assumptions}` — finance definitions that must stay explicit and NEVER be inferred (status SoT, valuation/costing basis, block/line semantics, FX basis). Rendered as brief Open Questions; the workflow never resolves them.
- `{finance_terminology}` — canonical finance terms to use consistently (per `finance-presentation`).
- `{finance_must_not_infer}` — accounting-truth acceptance constraints (no invented figures, account mappings, or valuation methods; missing → mark, never impute).
- The pass's `must_preserve_capabilities` fold into `{must_support_capabilities}`; `dropped_capability_flags` cross-check into `{dropped_capabilities}`; `implied_surfaces` feed `{spawned_surfaces}` via §5f — capability/surface outputs travel the existing vars, no new ones needed.

## Ledger-archetype pass (`{is_ledger_surface}` / `{ledger_view}`) — classify the archetype, never the layout

Set in step-01 §3g. Asked whenever `{is_finance_surface}` is true OR the rows are quantity/stock movements
(finance-shaped is the PRE-FILTER for asking, never the answer — a ledger need not carry money, and most
finance surfaces are worklists). Captures WHICH ARCHETYPE the surface is, never how to draw it:

- `{is_ledger_surface}` — `true` iff rows are **movements over time on an account** AND a column is meant
  to be **summed/accumulated**. A table that merely sorts by a date is a worklist. A route NAME is never
  evidence.
- `{ledger_view}` — a STRUCTURED VALUE, never a yes/no: `not-a-ledger` | `register` (movements, no running
  balance, most-recent-first) | `running-balance` (cumulative column, **oldest-first** — the one sanctioned
  exception to a most-recent-first default). `not-a-ledger` is a first-class, legal, expected answer.
  Rendered at brief §2d; gate class **(g)** in step-03 fires on ABSENCE of the field, never on a value.
- `{ledger_archetype_policy_source}` — the file in this project's policy chain that DEFINES the ledger
  archetype (the project `docs/design-policy.md` section, or the overlay it names as parent), or empty when
  none resolves. **Detected from what the policy DECLARES** (frontmatter `declares_archetypes:`, falling back
  to a ledger section heading), **never from a hardcoded family or project list** — so a project that starts
  inheriting the overlay is picked up the day it does.
- **Empty source ⇒ classify anyway, then record an Open Question.** The classification is true regardless of
  which policy a project inherits; the archetype RULES are not. Never fabricate rules and never import another
  project's ledger text — a brief field whose rules no consumer defines is a reader with no writer.

## Live-process pass (`{is_live_process_surface}` + `{runtime_behavior_contract}`) — capture time, never widgets

Set in step-01 §3c only when the surface's primary job is watching/controlling a long-running in-flight process (a scrape/download run, an import, a sweep, a sync, a batch job); `false`/empty for CRUD and finished-output surfaces. Closes the runtime-behavior contract-dimension-gap (`docs/fork-gaps.md` 2026-07-03): the gather's other axes are all *static*, so a surface whose whole job is change over time handed the designer a data shape and the temporal contract never entered the design lane — the redesign depicted one moment of a process. Captured inline (no skill yet — extract to one if a second caller appears):

- `{is_live_process_surface}` — gates §3c, brief §2c, and the §5f state-variant frames.
- `{runtime_behavior_contract}` — five facts, **derived from the driving code's own state enums/messages/storage writes, never invented** (greenfield: from the spec per §1c, unknowns degrade to Open Questions): (1) run lifecycle state machine — states, transitions, triggers; (2) per-item states incl. every failure/partial lane; (3) update transport & **staleness budget** (staleness is a designed property — the design may not promise liveness the plumbing can't deliver); (4) control verbs as outcomes with real semantics (drains vs kills, resumable vs restart); (5) available progress signals (signals only — the derivation/presentation is the designer's). Unresolved semantics travel inside the contract as Open Questions, never resolved here.
- Routing: each operator-distinct lifecycle state → a `{primary}--{state}` **state-variant frame** in `{spawned_surfaces}` (§5f item 4 — the film-strip is how a static brief communicates a dynamic mechanism; brief-level twin of `design-implement`'s state axis). Control verbs that invoke actions cross-check the §3 mutation-derivation audit. Motion/transition verification stays ceded downstream (`design-review` / `verify`) — the brief carries states + cadence, not animations.

## Interaction-model pass (`{is_processing_cockpit}` + `{interaction_model_contract}`) — capture the operation, never key maps

Set in step-01 §3d only when the surface is a **processing cockpit**: `{page_mode}` = `operational` AND §2 user context is expert / high-frequency / keyboard-first (a queue cleared one item at a time at speed); `false`/empty for occasional operational surfaces, dashboards, chrome, and any surface not repeatedly committing per-item decisions. Closes the interaction-model **contract-dimension-gap** (`docs/fork-gaps.md` 2026-07-11): the gather's other axes are all *static* (what to show, composition, data, evidence), so a keyboard-first speed cockpit handed the designer a beautiful surface with no operation model — keyboard flow, per-item commit→advance momentum, and consequence-preview-before-irreversible-commit were discovered by driving a prototype, even though §2 (keyboard-first) + §1 (speed metrics) already carried the signal. Captured inline (no skill yet — extract if a second caller appears):

- `{is_processing_cockpit}` — gates §3d and brief §4f. Produces NO new frames (cross-cutting behavior contract, like §2c — not a Surface-Inventory entry).
- `{interaction_model_contract}` — five facts, **derived from §1 (`{must_support_capabilities}` verbs), §2 (user context), the §3 mutation audit, and §2b/§4d basis for any written figure — never invented**: (1) operation surface — keyboard-first vs pointer, with a persistent shortcut affordance; (2) per-item action set & commit weight (reversible vs irreversible/high-stakes — immutable key / money / partner write); (3) momentum after commit (auto-advance vs manual to the next *actionable* item, with an undo window); (4) consequence-preview — which irreversible verbs must show what the commit writes (record + derived figure) BEFORE committing; (5) confidence-scaled effort (one-action fast path when confident; forced full decision when ambiguous — no rubber-stamp). Unresolved semantics travel inside the contract as Open Questions.
- Routing: per-item verbs cross-check the §3 mutation-derivation audit (like §3c control verbs); a preview showing a cost/KPI figure inherits the §2b/§4d DERIVED-vs-PERSISTED basis rule. Keyboard-focus/animation verification stays ceded downstream (`design-review` / `verify`) — the brief carries the operation model, not the bindings.

## Operator-domain pass (`{operator_domain_present}` + the `{operator_*}` block) — capture WHO the operator is + what to SHOW before ASK, never layout

Set in step-01 §3e only when `{is_processing_cockpit}` = `true` (co-fires with §3d — same gate). Produced by the `operator-domain-pass` skill (inline fallback if not synced), which SELECTS from `docs/<operator>-operational-profile.md` and never invents operator facts. Closes the operator-domain **contract-dimension-gap** (`docs/fork-gaps.md` 2026-07-18): §3d captures how the operator DRIVES the surface but nothing captured WHO the operator is or what the system must show before it asks, so M6 shipped domain-blind (the clerk-works-blind defect — asking for identifiers before showing what the system already knows). Twin of the §3b finance-domain pass, for OPERATOR ROLE instead of MONEY. Produces NO new frames (cross-cutting operator-meaning contract rendered into brief §4f alongside the interaction model). **HALT-on-missing-profile**: if `{is_processing_cockpit}` and no profile resolves, §3e emits no appendix and surfaces the blocking diagnostic — the handoff does not proceed on generic cockpit doctrine.

- `{operator_domain_present}` — `true` iff §3e ran, a profile resolved, AND the internal-consistency validation gate passed. Gates the brief §4f Operator-domain sub-section render in step-03.
- `{operator_detected}` — the operator identity (e.g. `warehouse-clerk`). A §1 context signal — does NOT set `{page_mode}` or composition.
- `{operator_role}` — one paragraph: identity · trust relationship · expertise · frequency (from the profile).
- `{operator_trust_boundary}` — `may_decide` / `may_not_decide` (owner-gated / verification-required outcomes) / `write_trust` (which operator writes are verifiable vs. taken on trust).
- `{operator_decides}` — per decision, the one outcome the operator must commit (aligned to `decision_points`).
- `{operator_known_before_ask}` — per decision, the facts the system resolves + surfaces BEFORE that ask.
- `{operator_evidence_required}` — per decision, what must be on-screen for that decision (fills M6's "which evidence").
- `{operator_forbidden_asks}` — per decision, the asks the surface must NOT make there (e.g. asking for an identifier the system already holds).
- `{operator_must_not_infer}` — top-level operator-truth constraints (don't guess identity the operator can't confirm; don't ask the operator to decide outside the trust boundary). 1:1 with the profile; never folded into `{operator_forbidden_asks}`.
- `{operator_ordering_invariants}` — top-level ordering the design must honour (expected-contents-first → identity-before-identifier → evidence-before-input, plus operator-specific). 1:1 with the profile.
- `{operator_policy_collisions}` — open questions where operator meaning collides with `docs/design-policy.md`; rendered as brief Open Questions, **never resolved here** (a human decides + records which side wins). `none` when clean.
- Validation gate (step-01 §3e step 8, runs on BOTH skill + fallback paths): decision-completeness · ordering-respected · no-boundary-contradiction. Any failure ⇒ handoff unverified, must be revised naming the failing check.

## Viewport & responsive pass (`{viewport_present}` + the `{viewport_*}` block) — the per-surface viewport CONTRACT the page-shell composition otherwise leaves implicit

Set in step-01 §3f, on EVERY `{surface_class} == page` run (skipped for `chrome`, which already captures `nav-desktop` vs `nav-mobile-drawer` breakpoints — step-01 §0). Closes the **viewport contract-dimension gap**: owner content surfaces had no responsive doctrine and the gather ran no structured viewport pass, so page briefs shipped desktop-blind (the freeform §5 `constraints — responsive breakpoints` line was left empty). Sources its values from the project `docs/design-policy.md §8` (surface-class → viewport policy) — NEVER invented. Twin of the §3b finance-domain / §3e operator-domain passes, for VIEWPORT. Produces NO new frames (a cross-cutting page-shell contract rendered into brief §4g). **WARN-on-open-ambition (warn-then-gate)**: while an owner class's mobile ambition is still OPEN in policy §8.3, §3f emits a loud diagnostic and marks the brief `unverified` / `pending-policy` but **LETS THE HANDOFF CONTINUE** — it does not freeze all owner work, and it still never fabricates a posture (the owner fields render `pending`). A small follow-up flips this warn to a hard HALT once the owner sets the ambition. (Missing/partial fields and policy contradictions still **FAIL hard** — see the gate.)

- `{viewport_present}` — `true` iff §3f ran, the surface's viewport class resolved against policy §8, the contract is fully populated (all six fields), AND the validation gate passed with no hard-fail and no pending. Gates the brief §4g Viewport & responsive render in step-03; a `false` on a `page` run means the handoff is `unverified` (below).
- `{viewport_pending_policy}` — `true` when the ONLY reason `{viewport_present}` is false is an OPEN owner ambition (the warn-only class (d) below): the brief is `unverified` / `pending-policy` but still emitted and the handoff CONTINUES. A hard-fail (class a/b/c) leaves this `false` and the brief is not deliverable.
- `{viewport_surface_class}` — the policy §8.1 class the target maps to: `clerk_bench` | `owner_dashboards_worklists` | `owner_approvals_recovery_reimbursements` | `owner_listings_catalog` (project policy §8.1 enumerates the classes; a project with a different surface taxonomy names its own). Resolved by matching `{route}` against §8.1's class→route table — **NOT `{surface_class}`** (which is the orthogonal `page`|`chrome` axis; do not conflate the two). Unmappable ⇒ open question, never a guessed class.
- `{primary_viewport_class}` — the surface's viewport posture: `desktop-only` | `desktop-primary, tablet-degraded` | `tablet-down` | `mobile-first`. For a DECIDED class auto-filled from policy §8.2 **as that class decided it** (a decided class may be `desktop-only` OR `mobile-first`/handheld-first — never assume desktop); for an owner class read from policy §8.3 ONLY once the owner has set the ambition — while OPEN it is unresolvable and §3f WARNs (pending-policy, continues).
- `{viewport_breakpoints}` — named breakpoints + px ranges the layout responds at (e.g. `desktop ≥1280 · tablet 768–1279 · phone <768`). Decided class: **as policy §8.2 decides** — e.g. a desktop-only class `desktop-only ≥1280px, landscape`, or a mobile-first class `phone viewport, portrait`. Owner: from policy once set — never invented while OPEN.
- `{viewport_min_tap_target}` — minimum interactive hit area (e.g. `44×44px`). Desktop-only bench class: `n/a` (keyboard + hardware scanner); a mobile-first class carries a real tap-target from policy. Owner: from policy once set.
- `{viewport_overflow_rules}` — scroll/overflow behaviour (which regions scroll vs reflow; is horizontal scroll allowed). From policy per class.
- `{canonical_viewport}` — **(artifact-labeling half, step-01 §3f.4b)** the ONE viewport the surface's interaction model is designed at and judged against. **DERIVED from `{primary_viewport_class}`, never chosen**: `mobile-first`/handheld-first ⇒ phone portrait (375×812 reference); `desktop-only`/`desktop-primary` ⇒ desktop ≥1280 landscape (1440×900 reference); `tablet-down` ⇒ the policy's named tablet reference. Read verbatim from a project policy's canonical-vs-additive subsection when one exists (e.g. cash-recovery `docs/design-policy.md` §8.2c). Exactly one value — a surface with two canonical viewports has none. **Unset on an owner class whose §8.3 ambition is OPEN** (no decided posture to mark). Consumed by brief §4g (the canonical/additive block) and, critically, brief **§7 "Per-frame outputs"** — the deliverable-format line a designer actually acts on, which previously hardcoded desktop width for every brief regardless of posture. Gate class (e) fires when this is unset on a DECIDED class.
- `{additive_viewports}` — the other `{viewport_breakpoints}` entries, each an **additive verification render**: proof that the canonical interaction model survives a different container, NOT a co-equal design. An additive render may not introduce a control, affordance, or information hierarchy the canonical render lacks (a handheld-first surface's desktop render is *a wider phone*). Anything in `{viewport_device_exclusions}` belongs to NEITHER list and is not rendered at all — a phone comp of a desktop-only bench surface is a policy violation, not an additive check.
- `{handheld_declaration}` — **(artifact-COMPOSITION half, step-01 §3f.4c)** the five-field Handheld-First Declaration a handheld-first `page` brief must carry: `surface class` · `canonical viewport` · `additive viewports` (`none` legal) · `scan/next-step loop` (a LOOP — trigger → feedback → next — never a feature list) · `offline/degraded state treatment` (which degraded states are first-class + the statement that they are drawn as states OF this surface). Assembled, never invented: fields 1–3 restate `{viewport_surface_class}` / `{canonical_viewport}` / `{additive_viewports}`; field 4 comes from `{core_job}` and the §3c contract; field 5 from the class's offline policy and the §5f state-variant frames. `TBD` / `responsive` / `see policy` are **non-answers** and fail. Contract, rules B1–B7, failure shapes, golden cases: **`shared/operator-artifact-contract.md`** (do not restate it here or in a project policy). **On a table-first surface, §7 must additionally carry the B7 in-surface composition spec** (compressed operational stack, not a dashboard opener) — a separate gate-(f) condition, since the five declaration fields plus the artifact sequence can all be present and still commission a hero-plus-chip-wall opener. **Unset — and gate class (f) does not fire — on a desktop-only class or an OPEN owner ambition.** Consumed by brief §4g and §7.
- `{viewport_device_exclusions}` — devices the surface is explicitly NOT expected to be operable on, **per the class's decided posture**: a desktop-only-decided class excludes `phone, tablet` (a mobile/faux-mobile UI is a policy VIOLATION); a mobile-first-decided class excludes nothing on mobile and treats desktop as additive-only (a desktop-only mouse-dependent layout is the violation). Owner: `usable_on_phone == false` ⇒ phone excluded.
- Validation gate (step-01 §3f, runs on both the auto-fill and policy-read paths) — **three rule classes, don't conflate them:**
  - **HARD FAIL** (brief not deliverable, must be revised naming the failing check): (a) `{viewport_surface_class}` unresolved; (b) **missing/partial contract** — any of the six fields blank on a clerk surface, or on an owner surface whose ambition is SET; (c) **policy contradiction** — a field contradicts `docs/design-policy.md §8`, including a desktop-only bench-class surface marked mobile/tablet-supported (that fails, it never warns).
  - **HARD FAIL, cont.:** (e) **canonical viewport undeclared on a DECIDED class** — `{canonical_viewport}` unset, two viewports marked canonical, or brief §7 not naming it as the render target with the rest marked additive. (b) asks *is the posture recorded?*; (e) asks *will the deliverable be DRAWN and READ at that posture?* A brief can pass (b) with a perfect §4g table and still tell the designer to render desktop-first.
